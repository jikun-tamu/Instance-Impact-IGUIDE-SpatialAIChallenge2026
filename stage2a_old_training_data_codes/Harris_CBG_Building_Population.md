# Harris CBG Building Population Dataset Notes

## Description of the dataset and its purpose

This project contains multiple derived datasets that connect Harris County buildings to Census Block Group (CBG) context using `GEOID`.

Primary purpose:
- Estimate building-level population/occupancy from spatial and demographic inputs.
- Aggregate building estimates back to CBG level for comparison with ACS reference values.
- Provide ML-ready labels (`ml_dataset/labels.csv`) for model training.

Important interpretation:
- `estimated_population` is a model/rule-based estimate, not direct measured ground truth at building level.
- CBG-level ACS columns in validation files are benchmark/reference values from Census products.

## File structure and naming conventions

Top-level outputs and working files:
- `harris_county_building_population_estimates.csv`: building-level estimated results.
- `harris_county_buildings_with_population.geojson`: spatial building polygons with estimated population attributes.
- `harris_county_cbg_validation.csv`: CBG-keyed comparison table (ACS-side fields and, when produced, aggregated estimated fields).
- `building_population_ml_dataset.csv`: small ML-oriented subset/example table.
- `ml_dataset/labels.csv`: main ML label table generated by pipeline notebook.
- `ml_dataset/crops/` and `ml_dataset/masks/`: image crops and masks keyed by `building_uid`.

Naming patterns:
- `harris_county_*`: county-level outputs from the geospatial estimation workflow.
- `ml_dataset/*`: machine-learning training artifacts.
- `*_validation.csv`: CBG-level aggregate/check table.

## Input/output format explanation

### Core identifiers
- `building_uid`: unique building instance ID in ML datasets.
- `GEOID`: Census Block Group identifier used to map building rows to CBG rows.

### Key file formats
- CSV (`.csv`): tabular attributes, no geometry object.
- GeoJSON (`.geojson`): building geometry + attributes (`estimated_population`, `GEOID`, etc.).
- Notebook (`.ipynb`): processing logic and export steps.

### Typical field roles
- Building-level estimate fields:
  - `estimated_population`
  - `building_type`
  - `estimated_units`
  - `quality_flag` or `classification_source`
- CBG demographic/reference fields:
  - `total_housing_units`
  - `occupied_housing_units`
  - `pop_*` (ACS structure-type population fields)
  - `occupancy_rate`, `ppu_*` (derived CBG ratios)

## Preprocessing details (if applicable)

The notebooks implement coordinate-based spatial assignment:

1. Build or load building geometries (from `Texas.geojson` in `code.ipynb`, and from xBD polygons in `building_population_pipeline.ipynb`).
2. Compute building centroid coordinates.
3. Spatially join building centroids to TIGER/Line CBG polygons (`within`) to assign `GEOID`.
4. Attach ACS-based CBG attributes/ratios by `GEOID`.
5. Optionally join parcel attributes for land-use-driven classification.
6. Estimate `estimated_population` using unit and occupancy logic.

Mapping behavior:
- Many buildings map to one CBG (`many-to-one` by `GEOID`).
- Not a one-to-one building-CBG pairing.

Input-source usage by notebook:
- `code.ipynb`: uses parcels + `Texas.geojson` + TIGER/Line CBG boundaries + ACS API.
- `building_population_pipeline.ipynb`: uses parcels + TIGER/Line CBG boundaries + ACS API + xBD building polygons (not `Texas.geojson`).
- `building_population_model.ipynb`: trains from `ml_dataset/labels.csv` and does not ingest upstream geospatial source files directly.

## Train/val/test split method

`building_population_model.ipynb` uses a grouped split to reduce spatial leakage:
- Method: `GroupShuffleSplit`
- Group key: `tile_base`
- Split: 80% train, 20% test (single split)

Interpretation:
- All buildings from the same image tile are kept together in either train or test.
- No explicit validation split is defined in the current notebook; validation metrics are reported on the held-out test split during training/evaluation steps.
